# Streamlined isolated Gerrit setup

Procedural companion to the skill and [Docker/API recipe](docker-and-api.md). Placeholders below are illustrative; do not reuse runtime values from another session. Reading this reference or loading the skill is not a run request; execution authority comes from the explicit invocation rules in `SKILL.md`.

## 1. Parallel read-only preflight

Read repository instructions and current status first. Preserve unrelated workspaces and files. Edit only the canonical `opencode/` tree. If `.opencode` is absent, do not create a symlink or configuration as part of this workflow.

Run independent checks in parallel, without creating resources:

- **Jujutsu/repository:** check operation state, bookmarks, configured identity, installed `jj` version and `jj gerrit upload --help`. Require the exact user-selected revset and inspect its full closure `mutable()::(<revset>)`. Derive base/ancestry only when local history makes one base unambiguous; stop on real ambiguity. For a fresh project default branch to `main` unless the user selected another target; never apply that default to existing state. Freeze exact full stable IDs and commit SHAs in the checkpoint.
- **Docker/image:** inspect Docker/Compose versions and context, image tag/digest/platform, image entrypoint/tools/paths, candidate loopback ports, and whether intended named resources already exist. A remote Docker context does not give the browser access to the daemon's loopback ports. For Docker Desktop/macOS endpoint and architecture checks, see [macOS setup notes](macos-setup.md#1-docker-desktop-and-host-locality).
- **Browser/CDP:** inspect existing browser processes, binaries, display availability, Node version and builtin WebSocket, and other already-present CDP clients. The [ai-browser guide](https://github.com/kyokley/ai-browser) is a reference, not a prerequisite to install. See [macOS setup notes](macos-setup.md) for Docker Desktop locality, app-bundle Brave discovery, native headed GUI checks, and a separate v3.14.4 token/account recovery observation. These are observations, not environment guarantees. Do not fetch, build, or install browser tools/dependencies without separate approval.

Resolve the exact user-selected revset, unambiguous base, image/platform, ports, and live resource state before writes. Create one restricted checkpoint outside the repository with verified decisions, owners, identities/IDs, paths, deadlines, and receipts. Never put token values, passwords, cookies, private keys, or reusable credentials in it.

## 2. Run-scope defaults and separate decisions

An explicit request to **run** a fresh ephemeral review for an exact revset authorizes the standard setup path through a configured Gerrit/project/base and the exact dry-run. No literal `RUN` keyword is required. Do not ask a routine permission checklist before each expected setup action. Announce derived defaults and proceed after read-only checks pass. A request to read, edit, or explain this skill is not a run request.

The default run scope covers fresh per-invocation Docker resources, a fresh isolated headed browser profile, account UI setup for the verified admin, `review-bot`, and `user`, the dedicated bot key, separate finite one-hour tokens, a fresh project, private bot/reviewer groups where needed, only missing project-local ACLs, seeding the exact approved base with temporary grants removed, a restricted checkpoint, and dry-run. Respect any explicit decline already active in the conversation or checkpoint; a later generic run request does not override it. If a declined optional token is skipped, report that REST/polling capability as unavailable rather than claiming it is configured.

Derive unique names per run from the current UTC date plus a fresh random suffix: Compose project `jj-gerrit-review-<date>-<suffix>`, Gerrit project `jj-review-<date>-<suffix>`, and private path `/tmp/opencode/jj-gerrit-review-<date>-<suffix>` (mode `0700`). Default account names are `admin`, `review-bot`, and `user`; derive token labels `bootstrap-<suffix>` and `review-<suffix>`. The image candidate is `gerritcodereview/gerrit:3.14.4-ubuntu24`; re-resolve its current immutable digest/platform each run. Derive HTTP, SSH, and CDP candidates from the run suffix in separate port ranges, then verify each is free. `18080`, `29418`, and `19222` are example candidates, not reservations. If occupied, choose and recheck another without prompting. Never reuse prior names, digests, ports, projects, volumes, or browser profiles.

Before writes, set a bounded overall setup deadline (default 15 minutes, or the caller's shorter budget) and explicit command deadlines; never leave browser/CDP/WebSocket/HTTP waits or shell/Docker commands unbounded. Bound local HTTP/REST/fetch/CDP/WebSocket operations to 5 seconds (maximum 10 seconds); give pull/init/readiness/SSH/push commands finite wall timeouts. Reserve restoration time within that overall deadline: at least two minutes, increased to cover the bounded temporary-grant removal and verification commands. Before granting temporary rights, require enough remaining setup time and admin-token validity for the bounded seed attempt plus that restoration reserve; otherwise do not grant or seed. Stop starting non-restoration work before the reserve begins, perform required restoration within its reserved budget, then persist verified state. At the overall deadline stop new operations, report any unverified restoration explicitly, and do not imply background continuation.

A named Jujutsu remote is a separate repository-configuration approval unless the current request explicitly includes that exact name and URL. Try the exact direct SSH URL in dry-run after server setup first. If runtime rejects it, defer the specific remote-name/URL question until the server is ready. Approval for one mapping permits only that mapping; preserve `origin` and all existing remotes.

Actual review upload requires fresh explicit approval after reporting the exact dry-run, closure, project, branch, and base. A dry-run is not upload approval or proof of connectivity. Submit/merge, replies, feedback polling, and cleanup are never part of the default run and require separate explicit authorization. Follow stricter host permission policy. Stop on collisions, unexpected accounts, failed admin membership/key proof, unexpected project/branch state, secrets that cannot be captured, token `401`/expiry, focus/model mismatch, or inability to verify temporary-grant removal; do not silently reuse, broaden, retry, or regenerate.

## 3. Create and verify the isolated instance

1. Under the explicit run request, use a new restricted temporary directory, unique Compose project, fresh uniquely named volumes, verified image digest/platform, and loopback-only HTTP/SSH bindings. Match image paths; do not mount over all of `/var/gerrit`.
2. Run init only against verified-empty volumes. Init may create the initial account and can upgrade existing state. Never reinitialize on resume. Configure and verify the selected auth mode before startup.
3. Check actual readiness, Gerrit version, persisted auth mode, exact loopback URLs/bindings, and container/image/project identity. A running container alone is not readiness.
4. Freeze a checkpoint before continuing. Assign one live browser owner. If several workers help, they must not race the same tab, account, dialog, or token.

## 4. Choose and own a safe browser

The explicit run request authorizes one fresh headed browser/profile for that invocation. Documentation-only loads do not launch it. Check an unused CDP port while holding a launch lock; never adopt an unknown listener or reuse a normal profile. The ai-browser launcher may reuse an occupied port and does not explicitly bind loopback, so do not use it unchanged. Launch with an explicit `--remote-debugging-address=127.0.0.1`, a checked `--remote-debugging-port=<port>`, and a unique `--user-data-dir=<private-path>`; include `--no-first-run` and `--no-default-browser-check`. Never add `--no-sandbox`.

On Linux, use headed mode only when the required display is usable. On macOS, check the native logged-in GUI session; unset `DISPLAY`/`WAYLAND_DISPLAY` alone does not prove that headed mode is unavailable. Do not silently install a browser or switch to headless. Verify process PID/arguments, profile mode `0700`, socket bound only to `127.0.0.1`, and `/json/version` for that exact owned endpoint. Keep this browser alive through the authorized setup; do not tear it down during handoff. See [macOS setup notes](macos-setup.md#2-headed-brave-and-cdp-on-macos).

## 5. Admin and account UI flow

1. Open the verified Gerrit URL. Follow rendered labels: Gerrit 3.14.4 may show **Sign in → Register → New Account**, not only **Become → New Account**. Inspect the signed-out chooser first. For the init-created admin, verify the exact signed-in profile and **Browse → Groups → Administrators → Members** before privileged use. Missing membership is a stop condition; never grant it as a workaround.
2. The run request covers standard account setup. For an authorized absent username, use **New Account** exactly once; it creates the account before profile completion. Resume its pending `gr-registration-dialog`; never click New Account again while that modal is pending.
3. Set only the approved username; do not invent email, display name, full name, or password. Scope the **Save** control to `gr-registration-dialog`, including open shadow roots; do not click Profile **Save Changes**. Verify exact username and account ID in Profile/header, reload, then verify again. Unexpected chooser entries, duplicate usernames, or mismatched IDs stop the run rather than trigger reuse or extra account creation.
4. With the verified automation account signed in, inspect Settings → SSH Keys before adding anything. Compare the exact authorized public `.pub` material; never read a private key. Add once through **Add New SSH Key** only if absent. Verify algorithm/material, **Valid** status, and persistence after reload for the same bot account ID. A key comment may be displayed differently; compare key material, not a partial comment.
5. Sign out only after any token modal is closed and its secret is stored. Register reviewer `user` only if absent; verify its ID after reload and leave the browser signed in as `user`. Do not give the reviewer bot credentials, admin membership, or unapproved project rights.

## 6. HTTP token generation: exact UI model and one-time capture

An enabled input and native browser validity are not proof Gerrit's component model received the values. In Gerrit 3.14.4, `gr-auth-token` has native inputs, Material host values, and component model fields (`newTokenId`, `newLifetime`). Require the exact label and finite lifetime in all three layers. Empty `newLifetime` can request the configured maximum; an observed `maxLifetime` was `unlimited`, so an empty field is unsafe.

1. Verify the exact Gerrit URL, signed-in username/account ID, non-secret token labels, absence of the requested label, and absence of a pending generated-token modal. Preserve existing labels such as `initialToken`; never read, delete, or revoke an existing token secret.
2. Inspect the rendered accepted duration and maximum. Use only the approved finite lifetime, default `1h`. Before every `Input.insertText`, verify that the exact target native input is the deepest `document.activeElement` reached through open shadow roots. Focus with trusted CDP mouse input, select existing text only when needed, and never press Enter. After each transition verify native value, Material host value, component model value, validity, and exact focus before the next insertion. If focus fails, use at most one bounded `scrollIntoView`/fresh-coordinate correction; recompute `getBoundingClientRect()` and visual viewport offsets, never guess DPR/scroll offsets. If the exact native input still is not focused, stop for a physical user click. Never type or click Generate from stale coordinates or a body-focused page.
3. Immediately before Generate, require exact label/lifetime in native, Material, and component layers; native/custom validation clear; `loading === false`; no label collision or pending modal; one visible Generate host; every host/Material/native button layer enabled; and a fresh composed-tree hit test with the target in the viewport and not occluded. Never set model fields directly or dispatch synthetic DOM events.
4. Prepare a secret-safe capture helper before the sole Generate click. Use one trusted CDP mouse press/release at the freshly verified host target. Check every CDP `exceptionDetails`; never hide errors behind optional chaining. Record only safe method/path/status and state. Never log request/response bodies, headers, cookies, modal text, or full DOM.
5. Gerrit 3.14.4 opens `dialog#generatedAuthTokenModal` before the REST result completes. Wait boundedly for the successful state. For the observed v3.14.4 render, the exact displayed secret is `#generatedAuthTokenModal #generatedAuthTokenDisplay .value` (a span; not necessarily a visible input). Capture only that existing rendered value directly into Node memory and write it once with exclusive create to the reserved path in a `0700` directory, mode `0600`. Never expose token-bearing CDP results through tool output, screenshots, logs, arguments, environment, source, checkpoint, or chat. Close that exact modal only after storage and mode/nonempty verification.
6. If capture code misses a value while the same verified account/label's generated-token modal remains open and the one-time rendered value is still present, recover that same value to the reserved file; do not Generate again, revoke, navigate, reload, or close first. If the value is absent/lost, stop and preserve state. Do not repair a failed generation by trying again.
7. Verify the finite displayed expiry and label after closing, reload, and verify persistence. Separately use the stored account-specific credential in a bounded read-only `GET /a/accounts/self`; require HTTP 200 and exact username/account ID. Never use the admin token as the bot credential or vice versa.

Do not reduce these gates to a blind Generate click. The cause of one observed CDP-focus failure was not proven; a physical user click restored the exact deep native focus, but that does not establish a root cause. Recompute coordinates after any layout/scroll change. Generate the admin token just before project/bootstrap work; generate the bot token only after seed-grant removal and as close as practical to authorized polling. On `401` or expiry, stop; never silently extend, refresh, or regenerate.

## 7. Minimal dependency-ordered runbook

1. A documentation/research request stops after local reads. An explicit request to run a fresh review with an exact revset starts the bounded default setup; announce the per-run names/paths/ports, run the parallel read-only preflight, and freeze the base/closure. Do not ask a routine approval checklist.
2. Provision the fresh digest-pinned loopback instance; verify exact image contents before named volumes, verify-empty volumes before one init, set auth before daemon start, and confirm HTTP readiness/version/bindings.
3. Match any init-created admin to its receipt, then verify rendered profile identity and Administrators membership. Create a first admin only if state is truly empty. Create missing `review-bot` and reviewer `user` accounts once with username-only fields; reload and verify account IDs.
4. Inspect bot SSH settings, add only the exact dedicated public key if absent, then verify exact algorithm/material, **Valid** status, persistence, and strict SSH using per-instance known_hosts. Do not read the private key.
5. Immediately before bootstrap, generate the finite admin token and capture it safely. Create the fresh project with `create_empty_commit:false`; verify the project is empty and target branch absent. Inspect inherited/local access plus one bounded `check.access` request per account/ref/permission. Create private bot/reviewer groups with the Administrators group UUID as owner, exact direct members, `visible_to_all:false`, and no creator; create the reviewer group only if needed. Add only missing project-local rules. On the new empty project, grant bot-group `create` and direct `push` only on `refs/heads/<branch>`, then seed only base and ancestors via the strict SSH key. Always remove exactly those temporary rules in `finally` and verify local absence/effective denial before proceeding. The bot HTTP token is not needed for SSH; generate it only once in the next step.
6. After bootstrap and successful temporary-grant removal, generate the finite bot token if not declined; verify its label/expiry after reload and its own-account REST self identity. SSH uses the dedicated key, not the HTTP token. If admin-token lifetime cannot cover the bounded bootstrap/grant-removal phase or a token returns 401/expired, stop without refresh/regeneration.
7. Recheck the exact revset and full mutable closure, base/branch head, project, effective permissions, strict SSH, and remote mode. Run the exact `jj gerrit upload --dry-run`; stop and report. A dry-run may list stack heads only and may not contact Gerrit. Leave the browser signed in as reviewer `user`. Obtain fresh explicit approval before any real upload; never upload, submit, or merge in the default run.
8. Keep the browser, instance, volumes, authorized remote, tokens, and checkpoint alive. Do not poll, reply/vote, or clean up unless separately requested and within token expiry; never silently regenerate an expired token.

## 8. Offline safety scenarios

Use these as documentation/static-review cases, not live account/token actions:

- Documentation-only invocation: perform local reads/edits only; never launch or change live state. A normal explicit exact-revset run request proceeds through standard setup defaults without a literal `RUN` word or repeated confirmation checklist.
- Derive the base from local history only when unambiguous; otherwise ask. Default a new project's branch to `main` unless the user specified another branch; never apply that default to existing state.
- Under the active run request, sign-in for read-only verification of the init-created `admin` is in setup scope. If rendered Administrators membership is absent/unverifiable, stop privileged setup; never grant membership as a workaround. When profile identity and group membership match, reuse that exact account ID without creating a duplicate.
- Lifetime native input reads `1h`, but Material or `gr-auth-token.newLifetime` is empty: disable the Generate gate; do not click.
- Token fields differ across native, Material, and model layers: do not Generate. If exact deep focus cannot be verified after one bounded geometry correction, stop for a physical user click; never type into `body` or set model values directly.
- A trusted click creates the requested non-secret token label and the generated modal remains open, but capture misses: inspect only non-secret structure, then recover only the exact existing rendered display into the reserved file. If the value is lost/unavailable, preserve state and stop; never retry Generate or revoke.
- A fresh automation/reviewer username is already assigned, or a project/branch/base is not new and empty as expected: stop; never hijack, overwrite, force-push, or reuse.
- Merely loading this skill for documentation/review does not launch or change a live instance. A normal explicit request to run an exact-revset review does not need a magic word and covers expected private setup through dry-run without repeated confirmation prompts.
- An exact run request does not authorize repository config edits by implication. If a direct-URL dry-run is runtime-rejected, defer the unique named-remote approval until the server is ready. Approval for that name/URL authorizes only that mapping; preserve `origin`.
- A previously declined token or upload remains declined. Skip a declined bot token and report bot REST/polling unavailable; never interpret a later generic run request as reversing the decline.
- The native token input has the requested label but the active deep focus chain ends at `body`: do not type or generate. Recompute geometry, use at most one scroll/coordinate correction, verify the composed hit target and exact native focus, then stop for a physical click if focus still fails. Never use synthetic DOM events or set Material/model values directly.
- Gerrit v3.14.4's generated-token modal is open, its label is persisted, and the selector finds no visible input: inspect only non-secret structure, then capture only the exact rendered `#generatedAuthTokenDisplay .value` into Node memory if it remains available. If unavailable, preserve the modal and stop; never retry Generate or revoke.
- Temporary bot Create+direct-Push seed rules exist but branch seeding fails: remove only those exact rules in `finally`; verify direct create/push denial and preserved inherited access. If removal cannot be verified, stop and report cleanup incomplete.
- A direct URL fails runtime dry-run with `remote ... does not exist`: finish server setup first, then ask approval for only one absent unique remote name/exact URL. Preserve `origin`.
- Inherited access already allows bot read/review-push/forgeAuthor or reviewer read/Code-Review: do not add redundant local rules. If bot `forgeCommitter` is missing, add only that project-local rule; do not change `All-Projects`.
- Temporary Create+direct-Push seed rules fail cleanup/denial verification: stop and report incomplete; never add a broad `BLOCK` or claim cleanup succeeded.
- A bot HTTP token returns 401 or is expired while the SSH key remains usable: stop bot-HTTP/polling operations; do not refresh or regenerate silently.
- Dry-run says “Found 1 heads to push” while the full mutable closure contains multiple revisions: report both. Dry-run may be heads-only and may not contact Gerrit; it never authorizes a real upload.
- During polling, stop starting work when `remaining <= 0`, set each request timeout to `min(5 seconds, remaining budget)`, and cap backoff/sleep by the remainder; preserve the last full snapshot and a separate terminal receipt.
- Any HTTP/fetch/CDP/WebSocket/shell/Docker wait has an explicit timeout; no unbounded await/retry loop. Before temporary grants, reserve bounded restoration/verification time inside the overall deadline and admin-token validity; do not grant if the seed attempt plus reserve will not fit. Stop non-restoration work before the reserve begins. At the overall deadline, stop new operations, preserve checkpoint/live state, report any incomplete restoration, and do not imply background continuation.
